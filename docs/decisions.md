# Design decisions

Short log of choices that keep the code, docs and demo consistent. Add an
entry when a shared contract changes.

| # | Date | Decision | Why |
|---|---|---|---|
| D1 | 23 Oct | Prebuilding is allowed from 23 Oct; the "no code before the event" rule in older planning docs is superseded. | Organiser email, 23 Oct 15:41 IST. |
| D2 | 23 Oct | `docs/api_contract.md` is the single source for API routes. The README links to it instead of repeating route tables. | The old README route table (`/companies/{id}/kb`, `/analyze`, `/approvals`) disagreed with the contract and the final plan. |
| D3 | 23 Oct | Roles are `analyst`, `writer`, `bid_manager`, `admin`. `hr`, `finance`, `legal` are KB data scopes, not login roles. Only `bid_manager` (or `admin`) decides Gate 1, approves Gate 2 and confirms amendments. | The data pack's `allowed_roles` use these names; the code still has `viewer/reviewer` (README task 1.3). The rubric names role-based access, so an analyst being refused at Gate 1 is a demo moment. |
| D4 | 23 Oct | Graph order is `extract_key_facts → reconcile_corrigenda`. | Amendments must override the facts extracted from the base tender. `graph.py` currently runs them the other way round (README task 4.2). |
| D5 | 23 Oct | `finalize` stays as a terminal bookkeeping node after `write_no_bid_report` / `export_outputs`. | Records completion timing; not a business step. |
| D6 | 23 Oct | Model routing: Groq GPT-OSS 20B (fast), GPT-OSS 120B (strong), Gemini 3 Flash (planning + one drafted section), Prompt Guard 2 (injection). Code handles arithmetic, dates, gates, scoring, citation validity and exports. | Matches the free-tier quotas in `llm_routing_and_budget.json`. The routing loader does not yet read that file's `routing` section (README task 4.1). |
| D7 | 23 Oct | SQLite + in-process background threads are the default runtime; Postgres + pgvector, Celery and Redis are optional. | Zero-setup demo and fresh-clone setup are scored (MVP Readiness). |
| D8 | 23 Oct | Eligibility rules live in a config rule pack per procurement regime. | Reusability criterion: a second pack loading without code changes is the reuse proof. |
| D9 | 23 Oct | Contributors are the two team members only. | Team decision. |
| D10 | 23 Oct | Build in strictly sequential phases with one owner each, alternating [S] → [H]. Tasks are grouped by dependency so a phase never needs the other person's unfinished work. | Team decision: avoids both people editing the same area at once, and each phase maps cleanly to a branch merged into `main`. |
| D11 | 23 Oct | Default company ID is `NIMBUS-001`, the ID used by every data-pack file. | The code defaulted to `NIMBUS`, which matched no data. |
| D12 | 23 Oct | Fact seeding rules: `eligible_value_inr` = client-certified bidder share only (never total contract value); project `scope_tags` are factual, not similarity verdicts; every source column is kept in `raw`; person names are stored masked. | Keeps the PRJ-005 trap honest, leaves "similar work" to the rule/judge, avoids schema churn for extra columns (PQ-04 infra turnover), and keeps PII out of prompts by default. |
| D13 | 23 Oct | Postgres runs in Docker (`pgvector/pgvector:0.8.0-pg16`) on host port 5433; schema changes go through Alembic, with `init_db()` kept for zero-setup SQLite. Tests always use their own database (temp SQLite, or `TEST_DATABASE_URL`), never `DATABASE_URL`. | Same database for both of us without touching local installs; 5433 avoids a local Postgres on 5432; tests can no longer wipe dev data. Postgres caught a `varchar(64)` overflow that SQLite ignored, so a column-length test now runs on both. |
| D14 | 23 Oct | Ruff uses an explicit rule set (`E, F, W, I, UP, B`), allowing blind `except` and long lines. | Ruff 0.17's defaults flag the deliberate fail-soft pattern; pinning keeps lint results stable across versions. |
| D15 | 23 Oct | Developer commands live in `dev.py` (stdlib only, run via `uv run`); the Makefile just calls it. `demo_data/` is excluded from line-ending conversion. Relative SQLite paths resolve from the project root. | `make` is missing on Windows; Windows Git can rewrite CRLF/LF and break the manifest hashes; a cwd-relative SQLite path silently created a second empty database when commands ran from another folder. |
| D16 | 23 Oct | Keyword ranking is BM25 in Python over SQL-filtered candidates on both databases; vectors rank with pgvector on Postgres. Query rewrite is deterministic (acronyms + procurement phrasing), no LLM call. | Postgres `ts_rank_cd` has no IDF and scored ~15 points lower recall@6 on the gold set; one ranking path gives identical SQLite/Postgres results. At < ~1,000 chunks per scope this is fast; the GIN index stays for a SQL pre-filter if data grows. |
| D17 | 23 Oct | A company KB document with hidden or critical injected text is quarantined whole and not indexed; a tender file keeps its clean sections and only the hostile spans are removed. A corrigendum is detected by content (names itself / lists amendments), not by passing mentions. | Trap manifest TRAP-KB-01 vs TRAP-INJ-01/02/03: poisoned company evidence must never answer questions, but a tender with one hostile annex must still be analysable. |
| D18 | 23 Oct | Phase 2 review: only a hard-gate `gap` forces NO_BID (needs_action/needs_human add conditions); `commercial_risk` sums deductions; `eligibility_confidence` averages hard gates only; personnel availability uses `PersonnelRule.available_by`. | Matches `bid_scoring_policy.json` and `eligibility_gold.json`; the earlier behaviour turned v1 into NO_BID. |
| D19 | 23 Oct | Hard gates are the PQ table rows plus the single-entity clause, extracted and evaluated deterministically (`agents/prequalification.py`); other shredded requirements are never hard gates and never risks. The risk register is contract clauses vs approved positions (`agents/commercial_terms.py`). Key facts come from a sourced deterministic extractor first; an LLM only fills gaps. | Phase 4 review: heuristic shredding produced 34 "hard gates" and 237 risks, so CASE-1 scored 10.0 NO_BID. The PQ table is where eligibility is decided; it must be exact and auditable. |
| D20 | 23 Oct | Scoring inputs not derivable from the tender (strategic fit, technical-score estimate, delivery capacity) are configured in `agents/analysis_inputs.json` and labelled as demo estimates. | Honest about what is measured vs assumed; replace per tender, or compute later. |
| D21 | 23 Oct | Default LangGraph checkpointer = CHECKPOINT_URL, else the app database (Postgres), else `storage/checkpoints.sqlite`; tests force their own. | A run paused at Gate 1 must survive an API restart without extra setup. |
| D22 | 23 Oct | Request handlers commit explicitly before starting background work (file processing, graph runs, Gate 1 resume); refused Gate 1 attempts are audited in their own transaction. | The runner and ingestion write from their own threads/sessions; on SQLite an uncommitted request transaction would block them, and a rolled-back request would lose the refusal's audit entry. |
| D23 | 23 Oct | Corrigenda are read from their amendment tables (Part A existing/amended, Part B responses) into typed changes; amended values are re-read with the key-fact extractor so they carry the corrigendum citation; confirmed amendments apply to every analysis of that version, and impact mode reuses unaffected hard-gate results. | Phase 6 review: section-id diffing found no amendments and nothing was applied, so v2 equalled v1. Part B responses that only confirm the RFP are not changes; substantive ones are kept as clarifications. |
| D24 | 24 Oct | `dev.py evals` runs the real pipeline on TDR-001 in a fresh database (`storage/evals/`) and scores it with the matching rules written in the gold files (same file, page +/-1 and token F1 >= 0.6, or contains `locate_span`; per version; mandatory items only for mandatory recall). Verifiers never read expected labels. | Phase 8 review: the harness scored whatever `TDR-001` happened to be in the dev DB (0% on a fresh machine, 61.9% on another), matched by coincidental IDs, mixed v2 items into v1, and the claim verifier returned the gold label as its verdict. |
| D25 | 24 Oct | Requirement extraction rejoins wrapped PDF lines before sentence splitting and turns structured table rows into candidates (optional columns and amendment columns kept apart); table cells are read by clipping each cell's area. | Splitting at every line break cut clauses in half, and `Table.extract()` dropped word spaces; table-only requirements (personnel, SLA, key dates, corrigendum) were never extracted. |
| D26 | 24 Oct | Vector search compares only vectors from the current embedder (`embedding_model`); `dev.py reembed` regenerates stale ones in place. KB ingest re-indexes when the manifest entry or the embedder changes, not only when the file changes. | Switching hash -> bge-m3 (same 1024 dims) would otherwise rank queries against meaningless cross-model cosines without any error; narrowed `allowed_roles` would never reach the index. |
| D27 | 24 Oct | LangSmith is optional (`LANGSMITH_TRACING=true` + key). One global client redacts every run (manual and automatic) before it leaves the process; traces nest analysis_run -> graph -> node -> tool/retriever/LLM; a Gate 1 resume shares the analysis thread_id; tracing is configured in the caller thread, never in pooled workers. Provider keys in `.env` are exported to `os.environ` by `get_settings()`. | The SDKs read only `os.environ`, so `.env` keys never reached Groq/Gemini/LangSmith; `langsmith.configure` also sets a thread-local flag that stuck to worker threads. |
| D28 | 24 Oct | Requirements no rule can check get up to 3 candidate company-KB passages (hybrid search as the least-privileged role) and stay `needs_human`; the candidate set and BM25 index are built once per run. | Phase 4.4 routed them to a "RAG grader" that did not exist, so 230+ items had no evidence; restricted KB text must not appear in items analysts open. |
| D29 | 24 Oct | Drafting is its own graph and run (`mode=drafting`) started from the persisted analysis of the approved version; analysis lookups skip drafting runs; Gate 2 decisions are applied inside the graph and persisted with the run. | A bid approval must not repeat extraction and eligibility (time and model quota), and the reviewer's decision must survive the run being saved. |
